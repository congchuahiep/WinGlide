# MSIX packaging

Builds the Microsoft Store package (`WinGlide_<version>_x64.msix`) from the same
payload the MSI ships. The MSI and ZIP channels are unaffected: this folder only
adds a third way to install WinGlide.

## Contents

| File                   | Purpose                                                                     |
| ---------------------- | --------------------------------------------------------------------------- |
| `AppxManifest.xml`     | Manifest **template**; `build-msix.ps1` fills in the `{{...}}` placeholders |
| `Assets/`              | Tile and logo PNGs, generated by `tools/icons/gen.ts` and committed         |
| `build-msix.ps1`       | Stages the payload, rebuilds `resources.pri`, packs and optionally signs    |
| `identity.example.env` | Template for the three identity values                                      |

## Prerequisites

- **Windows 11** and the **Windows SDK** - `makepri.exe`, `makeappx.exe` and
  `signtool.exe` must exist under
  `C:\Program Files (x86)\Windows Kits\10\bin\<version>\x64`. The script picks the
  newest one it finds.
- **Rust** for the release build (`cargo build --release`).
- The three identity values (step 1).

The tiles in `Assets/` are generated from the SVGs in `assets/` and committed, so
they need no tooling here. To change the artwork, follow
[`tools/icons/README.md`](../tools/icons/README.md) and commit the regenerated
PNGs before building the package.

## 1. Provide the identity values

The package identity comes from Partner Center: **your product -> Product
management -> Product identity**. Copy the template once and fill it in:

```bash
cp packaging/identity.example.env .env
```

| Variable                     | Comes from                                   |
| ---------------------------- | -------------------------------------------- |
| `MSIX_IDENTITY_NAME`         | `Package/Identity/Name` (e.g. `1234Pub.WinGlide`) |
| `MSIX_PUBLISHER`             | `Package/Identity/Publisher` - keep the `CN=` prefix exactly as shown |
| `MSIX_PUBLISHER_DISPLAY_NAME`| `Package/Properties/PublisherDisplayName`    |

`.env` is gitignored. The values are public - every installed package exposes
them - but keeping them out of the repository lets a fork build under its own
publisher. The script reads the environment first and falls back to `.env`, so
CI can pass them as secrets instead.

## 2. Build the package

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build-msix.ps1
```

The script builds before it packs, with the flags that make a Store package:
`cargo build --release --no-default-features --features store`. The `store`
feature compiles the GitHub update check - and its HTTP client - out of the
binary: Windows updates a Store package itself, and offering a download from
outside the Store breaks Store policy. The MSI and ZIP builds keep the updater
and are built with a plain `cargo build --release`.

The two flavours never share a build directory: the script sets
`CARGO_TARGET_DIR=target\msix\cargo`, so `target\release` keeps whatever the MSI
and ZIP need. That costs one full compile the first time, and it means the order
the two builds run in never matters.

Output: `target\msix\WinGlide_<version>_x64.msix`. The version is read from
`Cargo.toml` and padded to four parts (`0.0.15` becomes `0.0.15.0`), because the
Store requires four.

| Switch                | Effect                                                                 |
| --------------------- | ---------------------------------------------------------------------- |
| `-Configuration debug`| Build and package `target\debug` instead of `target\release`            |
| `-NoSign`             | Skip signing (CI uses this; the Store re-signs the package)             |
| `-Register`           | Register the staged folder as a development package (see step 3)       |

The package is signed by default with a self-signed certificate kept in
`target\msix\`, because `Add-AppxPackage -Path` refuses an unsigned one
(`0x800B0100`). Windows still has to trust that certificate - see step 3.

What the script does, in order: builds the Store flavour; copies the exe, its
DLLs, the Windows App SDK runtime, the `resources.pri` and the language folders
into `target\msix\stage\`; fills the manifest; rebuilds `resources.pri` from
`Assets/`; packs; signs.

## 3. Run it on your machine

The quickest loop needs no certificate and no administrator rights:

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build-msix.ps1 -Register
```

This calls `Add-AppxPackage -Register` on the staged manifest, so the package
reports `IsDevelopmentMode: True`. Developer Mode must be enabled in Windows
settings. It behaves like a Store install - package identity, Start menu entry,
the real taskbar icon - while rebuilding is instant because there is no repack.

To install the signed file the script produces, Windows also has to trust the
certificate, and that check only looks in the **machine** store:

```powershell
# elevated shell
Import-Certificate -FilePath "$PWD\target\msix\dev-cert.cer" -CertStoreLocation Cert:\LocalMachine\TrustedPeople
Add-AppxPackage -Path "$PWD\target\msix\WinGlide_<version>_x64.msix"
```

> Importing the certificate into `CurrentUser\TrustedPeople` (or
> `CurrentUser\Root`) is **not** enough: installing still fails with
> `0x800B0109` "the root certificate ... must be trusted".

Installing over an existing package of the same version fails with the exact
same error code (`0x80073CFB`); remove it first:

```powershell
Get-AppxPackage *WinGlide* | Remove-AppxPackage
```

Bumping the version in `Cargo.toml` is the alternative when you want to keep the
old package around.

## 4. Upload to the Store

Submit `target\msix\WinGlide_<version>_x64.msix` with the Partner Center
submission. The Store re-signs the package with its own certificate, so the
dev signature is only for installing it on your own machine (CI passes `-NoSign`
for that reason). Do not ship `dev-cert.pfx`: it lives in `target/`, which is
gitignored, and must never be committed.

The manifest deliberately declares one architecture (x64) and
`MinVersion 10.0.22000.0` (Windows 11 21H2). Every new version needs a higher
`Cargo.toml` version, because the Store rejects a package whose version does not
increase.

## What behaves differently in the package

- **Start with Windows** goes through the `StartupTask` declared in the manifest,
  so the toggle also appears in Task Manager -> Startup. The Run key is not used:
  a packaged process writes it into a private hive the shell never reads.
- **Running as administrator** and the **update check** are gone. The Store
  requires an app that never asks for elevation and delivers updates itself.
  The update check is not merely hidden: the `store` feature compiles it out.
- The Start and taskbar icons come from `Assets/`, not from the icon embedded in
  the executable.

## Troubleshooting

| Symptom | Cause and fix |
| ------- | ------------- |
| `MSIX_IDENTITY_NAME is not set` | No `.env` and no environment variable; do step 1. |
| `makepri.exe not found` / `makeappx.exe not found` | Windows SDK missing, or only the ARM/x86 toolset is installed. |
| `0x800B0109` on install | Certificate not in `LocalMachine\TrustedPeople`; run the elevated command in step 3. |
| `0x80073CFB` on install | Same version already installed; remove it first. |
| Taskbar icon sits on a coloured square | `resources.pri` was not merged, or the `_altform-unplated` PNGs are missing. Rebuild and confirm both. |
| Blue tint behind the logo | `BackgroundColor` in the manifest is `transparent`; Windows then fills the tile with the accent colour. Use a real colour. |
| Start menu shows the old icon | Windows caches per package; change the version or remove the package before reinstalling. |

## Why the script rebuilds `resources.pri`

Windows does not find the `_altform-unplated` logos by file name alone - it looks
them up in `resources.pri`, and the Windows App SDK payload ships its own index.
Without the merge, Start and the taskbar fall back to a plated logo, which is the
coloured square that used to appear behind the icon.

Indexing the whole stage at once fails with duplicate
`Files/Microsoft.UI.Xaml/Assets/...` entries, because that folder brings its own
`resources.pri` along. The script therefore indexes a temporary directory holding
only `Assets/` and merges that index into the Windows App SDK one.
